# 콜드체인 차량 관제 - 계획 문서

> 버전: 1.0.0 | 작성일: 2026-07-31 | 상태: 승인
> 프로젝트 수준: Dynamic

---

## 1. 개요

### 1.1 목적

가상의 냉장 물류 차량이 보내는 위치·온도 텔레메트리를 MQTT로 수집하고
TimescaleDB에 저장하는 미니 관제 프로젝트를 구축한다.

이 프로젝트의 핵심 목적은 화면 기능을 많이 만드는 것이 아니라 다음 흐름을
작고 명확한 구조로 직접 검증하는 것이다.

```text
Vehicle Simulator -> MQTT Broker -> Telemetry Ingestor -> TimescaleDB
```

### 1.2 배경

기존 프로젝트에서는 차량 에뮬레이터가 HTTP API로 대량 데이터를 전송하고
RabbitMQ가 수신량과 DB 처리량의 차이를 완충했다. 리빌드에서는 MQTT 브로커를
차량 연결 지점으로 사용하고, 메시지 수집·검증·저장의 책임을 분리한다.

RabbitMQ는 초기 MVP에서 제외한다. 이후 알림, 통계, 외부 연동처럼 독립적인
비동기 처리가 실제로 필요할 때 수집기 뒤에 추가한다.

## 2. 목표

### 2.1 주요 목표

- [ ] 여러 가상 차량이 현실적인 텔레메트리를 MQTT로 발행한다.
- [ ] 수집기가 메시지를 검증하고 중복을 안전하게 처리한다.
- [ ] 차량의 시간 기반 이력을 TimescaleDB에 저장하고 조회한다.
- [ ] 연결 끊김, 지연, 중복, 재접속 폭주를 에뮬레이터로 재현한다.
- [ ] 구성요소별 책임과 데이터 흐름을 문서와 코드에서 일치시킨다.

### 2.2 제외 목표

- 실제 차량 단말기 및 물리 센서 연동
- 모바일 앱
- 관리자 자체 가입, 다중 역할과 세밀한 권한 관리
- Kubernetes 및 마이크로서비스 운영
- 머신러닝 기반 고장 예측
- RabbitMQ를 이용한 내부 이벤트 처리
- 상용 수준의 지도 및 배차 최적화

## 3. 범위

### 3.1 포함 범위

#### 차량 에뮬레이터

- 설정한 차량 수만큼 MQTT 클라이언트 실행
- 차량별 고유 ID와 증가하는 sequence 생성
- 위치, 속도, 방향, 적재함 온도, 문 상태 생성
- 정상 주행, 온도 상승, 연결 끊김 시나리오
- 연결 복구 후 적체 데이터 재전송

#### MQTT

- 차량별 telemetry 토픽 사용
- QoS 1 기반 발행 및 구독
- 개발 환경용 MQTT 브로커 구성

#### 텔레메트리 수집기

- MQTT 메시지 구독
- JSON 스키마 및 필수 필드 검증
- `vehicleId + sequence` 기준 멱등 처리
- 측정 시각과 서버 수신 시각을 분리해 기록
- 유효한 데이터를 TimescaleDB에 저장
- 잘못된 메시지를 로그로 식별

#### TimescaleDB

- 차량 기본 정보 저장
- 텔레메트리 hypertable 구성
- 차량과 시간 범위 기준 이력 조회
- 최신 차량 상태 조회

#### 관제 API와 웹

- 이메일과 비밀번호를 이용한 최소 관리자 인증
- 차량 등록, 수정, 활성화 및 목록 조회
- 전체 차량의 최신 상태와 관제 요약 조회
- 네이버 지도에서 전체 차량의 최신 위치와 상태 표시
- 차량별 온도·속도 이력 조회
- 차량 상세에서 과거 이동 경로 표시
- 온도 이상과 통신 두절 감지
- 이벤트 목록과 확인 처리
- dashboard, 차량 관리, 차량 상세, 이벤트 화면

#### 배포 기반

- Terraform 기반 단일 클라우드 VM 구성
- Docker Compose 기반 애플리케이션 배포
- 애플리케이션과 DB 데이터 볼륨 분리
- Terraform 검증과 데이터 보호 정책 문서화

#### 검증

- 단일 차량 정상 흐름 검증
- 다중 차량 동시 발행 검증
- 중복 메시지 저장 방지 검증
- 연결 복구 후 지연 메시지 저장 검증
- 처리량과 실패 건수를 로그와 쿼리로 확인

### 3.2 제외 범위

- RabbitMQ 및 별도 이벤트 Worker
- SMS, 이메일, 푸시 알림
- 실도로 지도 경로 데이터
- 다중 서버 고가용성과 자동 확장 구성

## 5. 비기능 요구사항

| 분류            | 요구사항                                                                           |
| --------------- | ---------------------------------------------------------------------------------- |
| Reliability     | MQTT QoS 1 중복 전달을 DB 멱등성으로 처리한다.                                     |
| Observability   | 수신, 저장, 거부, 중복 건수를 구조화 로그로 확인할 수 있다.                        |
| Performance     | 로컬 환경에서 100대가 1초마다 보내는 100 msg/s를 유실 없이 처리한다.               |
| Maintainability | simulator, ingestor, storage 책임을 서로 분리한다.                                 |
| Reproducibility | 로컬 인프라를 한 번의 Docker Compose 명령으로 실행할 수 있다.                      |
| Simplicity      | 성능 또는 기능 요구가 확인되기 전에는 RabbitMQ와 Redis를 추가하지 않는다.          |
| Data Integrity  | 처리한 메시지를 별도 접수 기록으로 식별하고 중복 저장을 방지한다.                  |
| Security        | 비밀번호를 안전하게 해시하고 서버에서 폐기 가능한 세션으로 관리자 접근을 보호한다. |
| Freshness       | 최신 차량 상태는 정상 연결에서 5초 이내 화면에 반영한다.                           |

## 6. 메시지 계약

초기 텔레메트리 메시지는 다음 필드를 기준으로 한다.

```json
{
  "schemaVersion": 1,
  "messageId": "65e76b44-05e2-4f66-9133-9203fa51369e",
  "vehicleId": "VH-001",
  "sessionId": "e06829f4-f031-4e17-8106-b06721cc962c",
  "sequence": 10452,
  "recordedAt": "2026-07-31T10:20:30.123Z",
  "location": {
    "latitude": 37.5665,
    "longitude": 126.978
  },
  "speedKph": 52.4,
  "heading": 128,
  "cargo": {
    "temperatureC": -17.8,
    "doorOpen": false
  }
}
```

초기 토픽 규칙:

```text
fleet/{vehicleId}/telemetry
```

## 7. 성공 기준

- [ ] Docker Compose로 MQTT 브로커와 TimescaleDB가 실행된다.
- [ ] 에뮬레이터 100대가 각각 1초 주기로 QoS 1 메시지를 발행한다.
- [ ] 10분간 60,000건 이상의 메시지를 수집한다.
- [ ] 정상 메시지의 저장 누락이 없다.
- [ ] 의도적으로 재전송한 중복 메시지가 추가 행으로 저장되지 않는다.
- [ ] 차량 ID와 시간 범위로 이력을 조회할 수 있다.
- [ ] 관제 dashboard에서 차량별 최신 상태와 전체 요약을 확인할 수 있다.
- [ ] 차량 상세 화면에서 온도·속도 이력과 이벤트를 확인할 수 있다.
- [ ] 네이버 지도 키가 있으면 최신 차량 위치와 과거 경로를 표시한다.
- [ ] 지도 키가 없어도 placeholder를 표시하며 나머지 기능은 정상 동작한다.
- [ ] 온도 이상과 통신 두절 시나리오에서 이벤트가 생성되고 복구 시 해제된다.
- [ ] 비인증 사용자는 로그인 화면으로 이동하고 인증된 관리자만 관제 기능을 사용한다.
- [ ] 정상 연결에서 최신 차량 상태가 5초 이내 자동 반영되고 연결 복구 후 최신 상태와 일치한다.
- [ ] 잘못된 메시지와 DB 저장 실패가 로그에서 구분된다.
- [ ] README만 보고 로컬 실행과 검증을 재현할 수 있다.
- [ ] Terraform 코드가 format과 validate 검사를 통과한다.

## 10. 아키텍처 고려사항

- 전체 코드는 하나의 Git 저장소와 pnpm workspace에서 관리한다.
- 하나의 저장소를 사용하되 simulator, ingestor, API, web은 각각 독립 실행 가능한
  애플리케이션으로 유지한다.
- 초기에는 함께 배포하지만 서비스 간 통신은 MQTT, HTTP, PostgreSQL처럼 실제
  네트워크 연결과 명시적인 계약을 사용한다.
- 특정 애플리케이션의 독립 배포·확장이 필요해지면 해당 디렉터리와 소유 계약을
  별도 저장소로 분리할 수 있게 경계를 유지한다.
- MQTT 브로커는 디바이스 연결과 메시지 전달을 담당한다.
- 수집기는 프로토콜 입력을 DB 모델로 변환하는 경계 역할을 담당한다.
- TimescaleDB는 텔레메트리 이력과 최소한의 차량 메타데이터만 보관한다.
- 최근 48시간의 메시지 접수 기록을 일반 PostgreSQL 테이블에 보관해
  TimescaleDB hypertable과 독립적으로 중복을 판별한다.
- 지연 데이터는 이력에 저장하되 최신 상태와 실시간 경보를 덮어쓰지 않는다.
- 통신 상태는 최신 측정값과 분리된 마지막 유효 실시간 수신 시각으로 판단한다.
- 온도 이상은 1초 발행 주기에서 3회 연속 초과 시 발생하고 3회 연속 정상 시
  해제한다.
- 네이버 지도 연동은 웹 컴포넌트에 격리하고, 키가 없으면 placeholder를 사용한다.
- 최신 상태 전송 기술은 고정하지 않고 지연·부하·복구 검증 결과를 ADR로 기록해 선택한다.
- 브라우저는 동일 origin의 상대 `/api/v1` 경로를 사용하고 reverse proxy가 API로 전달한다.
- RabbitMQ가 필요해지는 조건과 도입 위치는 Design 문서에 별도로 기록한다.
- 설계에서 확정한 TypeScript 기반 공용 계약과 독립 실행 앱 구조를 유지한다.

## 12. 향후 확장

MVP 완료 후 필요성이 확인된 항목만 별도 기능으로 계획한다.

- RabbitMQ 기반 알림·통계 Worker
- Redis 기반 최신 상태 캐시
- 지오펜스 및 경로 이탈 감지
- 차량 제어 명령 MQTT 토픽
- 모바일·외부 API·다중 서비스 인증이 필요할 때 JWT 또는 OAuth/OIDC 전환 검토
